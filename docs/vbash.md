# 虚拟 bash：语料分析与测试基准

> 归属（2026-11-04）：本文与 `testdata/vbash-bench/` 一起引入。用途是给 `tools/shell` 的
> 一个可能演进方向——**用自建虚拟 bash 替代外部 shell 进程**——提供事实依据与回归基准。
> 相关文档：`shell-tool.md`（`run_shell` 现状与 `Console`/`Lease` 契约）。

状态：**分析完成，基准可用**；虚拟 bash 本身尚未实施，本文不含任何实现承诺。

## 1 为什么需要这份分析

`run_shell` 当前把命令交给宿主的真实 shell（`tools/shell/shell.go` 的 `Resolve` + `exec`）。
若要改成进程内虚拟 bash，第一个问题不是"怎么写解释器"，而是**目标覆盖面**：
agent 实际发出的命令里，多少只需要"切分 + 执行 + 传退出码"，多少需要完整 shell 语义。

没有这个分布，任何实现都会陷入两个极端：要么做一个玩具、要么追求 bash 兼容。

本分析基于 **505 个会话、35062 条真实 `run_shell` 调用**（去重后 160065 条子命令、715 个不同程序）。
全部数字可复现：方法见 §7，用例见 `testdata/vbash-bench/`。

## 2 结论先行

| 结论 | 依据 |
|---|---|
| **67% 的命令不需要 shell 控制流** | T0（7.8%）+ T1（59.7%）只用到管道/串联/重定向 |
| **30% 的复杂度来自 heredoc，而非控制流** | T3 占 30.0%，其中 26.3% 的命令含 heredoc；控制流关键字合计 <6% |
| **引号状态机是唯一不能省的部分** | 23.9% 的命令在引号内含 `;`/`\|`/`&`，朴素按分隔符切分必错 |
| **heredoc 体占命令体积的 80%** | 17.0 MB / 21.4 MB；但 90% 是引号化的，体内可当字面字节 |
| **真正需要的展开很少** | 变量 4.4%、命令替换 2.7%、参数展开 0.11%；反引号/`[[ ]]`/`eval`/`trap` 全为 0 |
| **`cd` 是高频分隔符** | 58.4% 的命令以 `cd` 开头，必须做会话级 cwd 状态 |
| **真实语法错误率 <0.1%** | 35531 条回显中 syntax error 仅 31 条；不必兼容 corner case |

## 3 命令分层

按"实现虚拟 bash 需要多少语义才能跑通"分层（部分重叠，一条命令只归最高层）：

| 层级 | 特征 | 占比 | 字符中位 | 需要的能力 |
|---|---|---|---|---|
| **T0** | 单命令 + 参数 | 7.8% | 40 | 词法切分、参数透传 |
| **T1** | 管道 / 串联 / 重定向 | 59.7% | 127 | `\|` `&&` `\|\|` `;` `>` `2>&1`、退出码传递 |
| **T2** | 含变量或命令替换 | 2.6% | 316 | `$VAR` `$(...)` `${...}` |
| **T3** | heredoc 或控制流关键字 | 30.0% | 971 | heredoc 配对、`for`/`if`/函数 |
| | **合计** | **100.1%**（各项独立四舍五入） | | |

T0+T1 = **67.5%**，只需要一个"能正确切分、执行、传退出码"的执行器。

## 4 引号：最高优先级

| 特征 | 占全部命令 |
|---|---|
| 含双引号 | 68.2% |
| 含单引号 | 54.6% |
| 单双引号同现（嵌套） | 41.6% |
| **引号内出现分隔符**（`;` `\|` `&` 换行） | **23.9%** |
| 引号内真实换行（多行字符串） | 3.6% |
| `$'...'` ANSI-C 引用 | 0.2% |
| 反斜杠续行 | 0.4% |

**这是唯一的刚性要求**：任何按 `split(";|&")` 切分的实现会在近四分之一的命令上翻车。
必须实现引号状态机——单引号内无任何展开；双引号内仅 `$`、`` ` ``、`\`、`"` 有语义。

多行字符串占 3.6%（多行 commit message、多行文档），因此"按行切分"同样不可行。

## 5 heredoc：占比最高、语义最简单的部分

按**命令**计（分母 35062 条命令）：

| 指标 | 数值 |
|---|---|
| 含 heredoc 的命令 | 26.3% |
| 单命令含 ≥2 个 heredoc | 3.3%（最多 12 个） |
| heredoc 之后还有后续命令 | 21.2% |
| heredoc 体总字符 | 17.0 MB（占命令总体积 21.4 MB 的 80%） |

按**heredoc 出现次数**计（分母 10139 处）：

| 指标 | 数值 |
|---|---|
| 引号化 `<<'EOF'` / `<<"EOF"` | **90.0%**（9125 处） |
| 未引号化（体内展开） | 1.3%（129 处） |

> 口径差异值得注意：90% 是按处数算的；若按命令算，**99% 的含 heredoc 命令至少有一个引号化 heredoc**。
> 无论哪个口径，结论一致——绝大多数 heredoc 体内可当字面字节，不需要展开。

两个必须做对的点：

1. **heredoc 不是"命令结束"**——21.2% 的命令在终止符后还有命令（`cat > f <<'EOF' … EOF\nwc -l f`）。
2. **终止符必须按出现顺序逐个配对**——3.3% 的命令含多个 heredoc，体内还可能出现 `'''`/`"""`（python 三引号 2834+826 处）与相似的终止符行。

好消息是绝大多数引号化，体内可完全当字面字节传输，无需展开。

**最高频的具体用法是 `python3 - <<'PY'`**（6426 条，占全部调用 18.3%）——即模型用 python heredoc
当"文件改写引擎"。虚拟 bash 只需把 heredoc 体原样传给解释器，不必理解内容。

## 6 控制流与外部程序

### 6.1 控制流（合计 <6%，可后置）

| 构造 | 占比 |
|---|---|
| `for … do … done` | 3.8% |
| 子 shell `( )` | 0.7% |
| 行尾后台 `&` | 0.5% |
| `[ ]` / `test` | 0.3% |
| `if … then … fi` | 0.3% |
| 函数定义 | 0.2% |
| `while` / `until` | 0.2% |
| 命令分组 `{ ; }` | 0.3% |
| `case … esac` | 0.1% |
| **`[[ ]]`、`=~`、`eval`、`trap`、`((...))`、反引号、`<<<`** | **0** |

后一行这些在语料里一次都没出现过。可以明确不支持，遇到时报错即可。

### 6.2 外部程序：边界清楚

715 个不同程序，覆盖曲线：

| 覆盖 | 需要的程序数 |
|---|---|
| 50% | 5（`echo cd head grep sed`） |
| 80% | 11 |
| 90% | 17（末位 `wc`） |
| 95% | 30 |
| 99% | 124 |
| 100% | 715（其中 302 个只用过 1 次） |

按能否虚拟化分：

| 类别 | 占比 | 处理方式 |
|---|---|---|
| 文件/文本工具（`cat`/`grep`/`sed`/`head`/`ls`…） | 73.7% | 可在 vfs 上内建，前 15 个覆盖 60% 子命令 |
| 语言/构建（`go`/`python3`/`node`/`make`…） | 14.4% | **不可虚拟，直接透传宿主** |
| `git` | 5.1% | `log`/`status`/`diff` 占 87%，可选模拟 |
| 网络/远端（`curl`/`ssh`） | 2.6% | 透传；ssh 目标单一，需调用方注入 |
| 系统/硬件（`adb`/`debugfs`/`pkill`/`systemctl`…） | 2.1% | **不可虚拟，透传** |

因此合理的边界是：**虚拟 bash 负责"解析 + 展开 + 内建 + vfs 上的文件工具"，把构建/系统/网络三类透传宿主。**
这与 `tools/shell` 现有 `Console`/`Lease` 契约并不冲突——透传部分仍走 `exec`。

## 7 建议的实施顺序

按"性价比"排序，每步都能独立验证（`testdata/vbash-bench` 逐层给分）：

| 步 | 内容 | 覆盖 | 门槛 |
|---|---|---|---|
| 1 | 引号状态机 + 分隔符切分 + 退出码 | T0+T1 主体 | `T0=100,T1=100` |
| 2 | 重定向（`>` `>>` `<` `2>&1` `/dev/null`）+ `cd` 会话态 | T1 剩余 | 同上 |
| 3 | heredoc 精确配对（含多终止符、终止符后接命令） | T3h（26.3%） | `T3h≥90` |
| 4 | 变量 / 命令替换 / `~` 展开 | T2（2.6%） | `T2≥95` |
| 5 | `for` / `( )` 子 shell | 少量补齐 | 可选 |
| — | 明确不支持：`[[ ]]` `eval` `trap` 反引号 `((...))` `case` | — | 报错且不崩 |

第 1–2 步完成后即可覆盖 **67.5%** 的真实命令；第 3 步到 **93.8%**（67.5 + 26.3）。

## 8 分析方法（可复现）

1. **数据源**：调用方落盘的 agent 会话记录（含其归档卷），共 505 会话。会话文件是 `jsonl`，每条消息一行，工具调用在 `assistant` 消息的 `tool_calls` 字段。
2. **抽取**：`assistant` 消息的 `tool_calls` 中取 `run_shell`/`shell` 的 `command` 参数。
3. **词法扫描**：逐字符状态机处理单/双引号、`$'...'`、注释、heredoc，**把引号字面量与 heredoc 体掩码后**再匹配语法特征。
   这一步不可省：朴素正则会把 Markdown 反引号数成 shell 反引号（2776 次 vs 实际 0）、把 Python 里的 `select` 数成 shell 的 `select`（821 次 vs 实际 0）。
4. **分层**：见 §3 定义。
5. **基准**：`testdata/vbash-bench/` 中 193 条用例由真 bash 5.3 录制 golden，逐层比对 stdout/stderr/退出码。

## 9 基准的自我校验

测试集必须能区分好坏实现，否则没有价值。两个固定基准：

| 被测 | 结果 | 意义 |
|---|---|---|
| 真 bash 5.3 | **228/228（100%）** | 基准自身正确、golden 无漂移 |
| `tools/reference-naive.py`（故意朴素：盲切分隔符） | **88/193（45.6%）** | 能抓出"不做引号/heredoc"的典型错误 |

若某天朴素实现也能全绿，说明用例松了，需补强。

## 10 明确不做的事

- **不追求 bash 兼容**。语料中真实语法错误率 <0.1%，corner case 无收益。
- **不虚拟构建/系统/网络命令**。`go`/`python3`/`adb`/`systemctl` 等直接透传。
- **不实现作业控制**（`jobs`/`fg`/`bg`/`wait` 语义），行尾 `&` 只占 0.46%。
- **不改 `tools/shell` 的 `Console`/`Lease` 契约**。透传路径仍走 `exec`，虚拟层是它的一个可选前置。

## 11 遗留

- 语料来自单一使用者的会话，命令风格偏向 Go/Python 项目维护；其他场景（前端、数据）的分布可能不同。
- `ssh` 目标在语料中高度集中（单一内网主机），占比 3.9%；虚拟化时需要调用方注入远端语义，本库不应内置。
- heredoc 体 17 MB 若整体驻留内存，需要关注峰值；流式传输是更稳的选择。
